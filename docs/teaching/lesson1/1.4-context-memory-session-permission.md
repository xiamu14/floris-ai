# Lesson 1.4 Context, Memory, Session, and Permission

## 目标

Lesson 1.4 的目标不是做完整 Context Inspector、长期 memory 或真实权限系统，而是把 agent loop 需要依赖的四个 runtime 边界先放到正确位置：

- `ContextBuilder`：决定下一次 provider request 带入哪些 context sections。
- `MemoryStore`：提供最小内存 memory 读取能力，为后续 memory library 留接口。
- `SessionStore`：记录一次 run 里的 event sequence，为 replay、branch 和 persistence 留接口。
- `PermissionGate`：进入 tool execution path，即使第一版只返回 allow，也要让后续真实权限策略有固定插入点。

完成后，Lesson 1.5 的 `AgentLoop` 不再直接拼 prompt、直接调用 tool、直接把运行过程丢在临时变量里，而是通过这些边界组织一次 agent run。

## 当前状态

状态：implemented as runtime boundary

当前代码里已经实现 Lesson 1.4 的 runtime boundary：

- `BasicContextBuilder` 会生成结构化 context sections、messages 和粗略 token estimate。
- `ProjectInstructionLoader` 会从 workspace 根目录读取 `AGENTS.md` / `AGENT.md`。
- `InMemoryMemoryStore` 支持第一版 memory entry 写入、查询和禁用。
- `InMemorySessionStore` 会记录 agent events，供 demo、测试和 replay 观察。
- `NoopPermissionGate` 已进入 tool execution path，返回结构化 allow decision。

这些代码仍然不是完整产品级能力：

- 还没有 Context Window / Context Inspector。
- 还没有 context include / exclude。
- session 不是 persistence，只是内存事件列表。

## 为什么放在 AgentLoop state machine 之前

Agent loop 看起来可以先写成一个 `while` 循环，但这样很快会把 context、session、memory、permission 都混进主流程。Lesson 1.4 先做这些 stub，有三个作用：

- 让 provider request 的输入是结构化 context，而不是临时字符串。
- 让 tool execution 从第一天经过 permission boundary，后续替换成真实策略时不用重写 tool path。
- 让 run 过程有 session event 记录，后续 Web UI、MLflow trace、benchmark 都能复用同一套运行事实。

这一步追求接口稳定和可测试，不追求功能完整。

## 实现范围

### ContextBuilder

`ContextBuilder` 接收已解析的 agent profile、user message、recent messages、memory entries、tool results 和 workspace 信息，输出 `ContextSection[]`。

第一版 section 至少包含：

- `system`：来自 `AgentProfile.systemPrompt` 解析后的 prompt content。
- `project_instructions`：从 workspace 根目录读取 `AGENTS.md`。
- `recent_messages`：当前 thread 最近消息。
- `memory`：来自 `MemoryStore` 的相关 memory entries。
- `tool_results`：上一轮可进入 model context 的 tool result summary / context。

每个 section 必须有：

- `kind`
- `title`
- `content`
- `tokenEstimate`
- `source`

`tokenEstimate` 第一版使用 `Math.ceil(content.length / 4)`。这只是成本估算，不是 provider 精确 token 统计。

### Project instructions 读取规则

`AGENTS.md` 是第一版必须支持的 workspace instructions。它不是 system prompt 的一部分，而是独立的 `project_instructions` context section，方便后续 Context Inspector 展示来源、token 占用和 include / exclude 状态。

第一版读取规则：

- 默认只读取 workspace 根目录的 `AGENTS.md`。
- `AGENT.md` 和 `AGENTS.md` 语义一致；如果两者都存在，按 `AGENTS.md`、`AGENT.md` 的稳定顺序合并为同一个 `project_instructions` section。
- 缺失时不能让 run 失败，要在 context build result 里记录 skipped section 和原因。
- 读取失败时不要吞掉错误，要记录稳定 `code` 和可读 `message`，但第一版仍然继续构建其它 context。
- section `source` 要记录 workspace relative path，后续 UI 可以显示来源。
- 不读取任意绝对路径里的说明文件。类似用户全局偏好、Codex 全局规则、团队共享规则，后续通过 Global Memory / Project Settings / 明确 include 进入 runtime，不能由 ContextBuilder 私自扫描用户目录。

除了 `AGENTS.md`，第一版还可以按需读取这些内容，但不默认全文进入 context：

- global memory：用户偏好、长期规则、跨项目开发习惯。
- project memory：架构决策、已知问题、反复出现的项目经验。
- workspace metadata：`README.md`、`package.json`、`tsconfig.json`、测试配置和 build 配置，用于判断命令和技术栈。
- 当前 lesson 或任务相关文档：例如本节的 plan / teaching 文档，由用户消息或 tool 检索触发。

推荐实现：

```text

AgentLoop
  -> MemoryStore.listRelevant()
  -> ContextBuilder.build()
      -> AgentProfile.systemPrompt
      -> ProjectInstructionLoader.load(workspacePath)
      -> recent messages
      -> memory entries
      -> tool result summaries
  -> Provider request

```

`ProjectInstructionLoader` 只负责读取和描述 workspace instructions；`ContextBuilder` 负责把它们组装成有稳定顺序和 token estimate 的 sections。这样后续支持嵌套 `AGENTS.md`、global rules、secret redaction 或 Context Inspector 时，不需要重写 agent loop。

### MemoryStore

`MemoryStore` 第一版使用内存实现，支持：

- 新增 memory entry。
- 按 `scope`、`type`、`projectId`、`threadId` 查询。
- 禁用 memory entry。
- 返回选中的 memory entries，交给 `ContextBuilder` 组装。

Memory scope 保持通用 agent 语义，第一版只包含 `global`、`project`、`thread`。不要把 coding workflow 的 `branch` 硬编码成 memory scope；branch 是某些 workflow 的可选能力，后续如果需要分支级 context，可以放在 thread/session/branch store 或 context policy 里处理。

Lesson 1.4 不做 embedding、ranking、长期持久化，也不让 agent 自动写长期 memory。

### SessionStore

`InMemorySessionStore` 记录 agent run 的事件序列，支持：

- `appendEvent(event)`
- `listEvents({ threadId, branchId })`
- 保持写入顺序。
- 事件带 `id`、`type`、`threadId`、`branchId`、`parentId`、`createdAt`。

这个设计为后续 JSONL / SQLite persistence、branch tree 和 replay 留接口。Lesson 1.4 不做真实磁盘保存。

### PermissionGate

`PermissionGate` 第一版是 no-op allow，但必须出现在 tool execution path：

```text

Tool call requested
  -> PermissionGate.check
  -> ToolRegistry.execute
  -> SessionStore.appendEvent(tool result)

```

第一版返回结构化 decision：

- `decision: "allow"`
- `source: "default_noop"`
- `reason`
- `toolName`
- `createdAt`

后续真实权限系统替换实现即可，不改变 agent loop 和 tool registry 的调用方式。

## 数据流

```text

User message
  -> SessionStore.appendEvent(user_message)
  -> MemoryStore.listRelevant()
  -> ContextBuilder.build()
      -> system prompt section
      -> project instructions section
      -> recent messages section
      -> memory section
      -> tool result section
  -> SessionStore.appendEvent(context_built)
  -> ModelProvider.createMessage(context)
  -> model tool call
  -> PermissionGate.check(tool call)
  -> ToolRegistry.execute(tool call)
  -> SessionStore.appendEvent(tool_result)

```

MLflow trace 继续记录 runtime observation；`SessionStore` 记录产品级 run history。二者通过 `runId`、`threadId`、`branchId`、`toolCallId` 关联。

## 验收标准

Lesson 1.4 完成时，必须满足：

- `ContextBuilder` 能输出稳定顺序的 section list。
- `system` section 来自 `AgentProfile.systemPrompt`，不是 agent loop 临时硬编码。
- workspace 有 `AGENTS.md` 时，`project_instructions` section 会进入 context。
- `AGENTS.md` 缺失时不 crash，并记录 section 被跳过的原因。
- recent messages、memory entries、tool results 可以进入 context。
- 每个 context section 都有 token estimate。
- `InMemorySessionStore` 可以按 thread / branch 写入和读取事件，并保持顺序。
- session event 有 `id`、`type`、`threadId`、`branchId`、`parentId`、`createdAt`。
- no-op `PermissionGate` 在 tool execution 前被调用，并返回结构化 allow decision。
- tool path 不绕过 `PermissionGate`。
- `bun run typecheck`、`bun run test`、`bun run check` 通过。

## 暂不做

- 不做 Context Inspector UI。
- 不做 context 手动裁剪和编辑。
- 不做自动 compaction。
- 不做 embedding retrieval。
- 不做长期 memory 自动写入。
- 不做 JSONL / SQLite persistence。
- 不做真实权限策略、用户确认 UI 或审核 agent。
- 不做 secret scanner 的完整实现；只保留未来接入位置。

## 教学重点

讲解 Lesson 1.4 时，重点解释这几个问题：

- 为什么 context 要拆成 sections，而不是拼成一段大 prompt。
- 为什么 `system prompt` 是 context 的一部分，但来源必须是 agent profile / prompt store。
- 为什么 memory 和 session 是不同概念：memory 影响下一次 context，session 记录已经发生的事实。
- 为什么 no-op permission 也有价值：它固定了安全边界的位置。
- 为什么这些接口要先于完整 agent loop 建好：避免 Lesson 1.5 的 state machine 变成混合所有职责的大函数。
