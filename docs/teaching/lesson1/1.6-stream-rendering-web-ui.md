# Lesson 1.6 Stream Rendering Web UI

## 目标

Lesson 1.6 提供本地 stream rendering Web UI，让学习者和开发者可以直接看到 agent run 的用户可见过程。

它不只是把 CLI output 搬到网页，而是验证未来 Floris macOS app 也需要的 stream event contract。

这一轮开始，`apps/web` 使用 kanalabs 作为 Web UI。它可能在后续作为 production UI 嵌入 macOS desktop，因此主 chat 页面必须保持用户产品体验，不直接显示 debug tabs、Run Graph、trace 这类开发观察信息。

Lesson 1.6 还要提供运行时 state graph 可视化。它不是文档里的静态 Mermaid 图，而是从一次真实 run 的 session events 派生 `RunGraph`，再用 React Flow 展示 agent loop 的实际路径、tool call、permission、stop reason 和异常诊断。这个能力放在 debug 模式下可访问的独立页面，不进入主 chat 页面。

## 当前状态

状态：not implemented

CLI demo 可以继续作为 smoke script，但 Lesson 1.6 的主要交付是 Stream Web UI。

## 用户可见输出

Web UI 应该增量渲染：

- user message。
- assistant text delta。
- final assistant message。
- tool call started / finished。
- tool result summary。
- context build summary。
- stop reason 和 error state。

Debug 页面应该展示：

- Run Graph：展示一次 run 的 state graph、transition、tool path 和 diagnostics。
- stream events / session events timeline。
- MLflow trace id 或 trace link。

## 第一版边界

- 只做本地开发 UI，不做生产 macOS app。
- HTTP server 独立放在 `apps/server`，使用 Hono.js 官方 Bun runtime 模式，只依赖 `hono`，不使用 `@hono/node-server`。
- `apps/server` 是 production server app，不是临时脚本。它要按 Hono.js 项目方式组织，后续可以嵌入 macOS desktop，作为 kanalabs Web UI、产品 API 和 agent runtime 之间的 bridge。
- `apps/server` 会承载 `apps/web` 需要的用户功能、支付、订阅等 production API。
- `apps/server` 的产品 API 和 agent runtime control boundary 必须分开。支付、订阅、用户 API 可以是 production HTTP API；控制 agent runtime 的 private RPC 不能暴露为 public API。
- 第一阶段不为 agent runtime control 暴露 OpenAPI endpoint，不提供外部 SDK，不承诺其他进程可以直接调用 HTTP API 控制 Floris。
- `apps/server` 提供 `/runs` stream endpoint，负责把本机 runtime stream 转成 HTTP/SSE，服务 `apps/web` 开发和 debug 页面。
- `apps/web` 只做 UI，不组合 agent loop、provider、tool registry 或 permission gate。
- transport 第一版使用 SSE。
- Web UI 不实现 agent loop，只消费 runtime stream events。
- agent runtime 作为用户本机 child process 运行，拥有 agent loop、workspace、tool、permission 和 session 能力。
- `apps/server` 和 agent runtime 之间使用私有本机 RPC。第一版推荐 JSONL over stdio；后续可替换为 Unix domain socket、WebSocket 或其他本机 transport。
- 私有 RPC 只覆盖最小 control message，例如 start run、abort run、submit user message、respond permission。它不是 public command API。
- 主 chat 页面不显示 debug tabs，也不加隐藏或轻量 debug 入口；后续需要时再补。
- Run Graph、Events、Trace 放在 debug 模式下可访问的独立页面。
- stream event 不传 secret 原文。
- React Flow 只消费 `RunGraph` JSON，不进入 runtime core。
- MLflow trace 继续作为深度观察入口。

```text
apps/

      routes/
      components/
      features/chat/
      features/debug/
  server/
    src/
      app.ts
      main.ts

        routes/debug-runs.ts
        routes/users.ts

        runtime-process.ts
        stream-event-mapper.ts
      runs/
        run-service.ts
        run-store.ts

        user-service.ts

        billing-service.ts
      types/
        http.type.ts

        user.type.ts
        billing.type.ts
```

职责划分：

- `packages/agent-runtime`：agent loop、private runtime RPC、stream event contract、session event、RunGraph builder。
- `apps/server`：production Hono server app，负责产品 API、连接本机 runtime process、HTTP/SSE route、run orchestration、debug run 查询和错误映射。它不实现 agent loop。
- `apps/web`：kanalabs production chat UI 和 debug page UI，只消费 API。

`apps/server` 开发要求：

- Hono app 创建、server 启动、env 读取、route 注册要拆开，不把所有逻辑堆进入口文件。
- route 只处理 HTTP 输入输出，不能直接写 agent loop 或 runtime 细节。
- 产品 API route、runtime run route、debug route 分模块管理，不能混在同一个 route 文件里。
- runtime 连接、process lifecycle、RPC framing 放在 `runtime/`。
- run 状态、stream fan-out、debug 查询放在 `runs/`。
- 用户、支付、订阅等产品逻辑放入对应领域目录，例如 `users/`、`billing/`。
- SSE 编码、心跳、断开处理放在 `http/sse.ts` 或独立 helper。
- 错误统一映射为结构化 response / stream event，不能在 route 中散落 `try/catch`。
- 所有跨模块类型放在 `apps/server/src/types/*.type.ts`，保持和 runtime 类型边界清楚。
- 不为省事把 production chat、debug page、runtime RPC 和 Hono route 写在一个或几个大文件里。

后续有两条产品路线：

- macOS app 直接连接 agent runtime private RPC，Swift 负责更多 bridge 和 permission UI。
- macOS app 内嵌 `apps/server`，让 Hono server 连接 kanalabs Web UI、产品 API 和 agent runtime，Swift 主要承担 desktop shell、窗口、打包和少量系统能力。

Lesson 1.6 的 `apps/server` 要按第二条路线也能继续演进的标准来写。需要注意：`apps/server` 可以有 production product API，但 agent runtime control API 仍然是 private boundary，不作为 public server 能力暴露。

## Runtime Control Protocol

Floris 第一阶段不做 public command API。这里的 control protocol 只服务 desktop app / local bridge 和 runtime child process 之间的内部通信。

第一版采用保守原则：

- control message 保持最小，只覆盖启动 run、取消 run、用户输入、permission decision。
- 用户可见状态全部通过 stream event 输出，UI 基于 stream event 增量渲染。
- session event 是持久事实来源，stream event 是 UI / bridge 观察通道。
- private RPC 不绑定 HTTP，不暴露 OpenAPI，不作为外部兼容承诺。
- 第一版不引入大型 RPC framework。先实现一个小而明确的 JSONL over stdio protocol，围绕 Floris 的 run、stream event、permission 和 session contract 设计。
- 可以使用 parser / utility 级别的小依赖，但不要引入会自动暴露 method registry、remote endpoint、reflection 或通用 RPC server 能力的框架。
- 后续如果要给其他 agent 调用 Floris，单独设计 app-server / A2A capability、auth、permission scope 和 audit log，不复用第一阶段内部 RPC 作为 public API。

推荐数据流：

```text
apps/web
  -> Hono SSE endpoint in apps/server
  -> private runtime RPC client
  -> agent-runtime child process
  -> AgentStreamEvent
  -> SSE
  -> apps/web reducer
```

推荐实现边界：

```text
packages/agent-runtime/src/rpc/
  rpc-protocol.ts
  jsonl-reader.ts
  jsonl-writer.ts
  runtime-rpc-server.ts

apps/server/src/runtime/
  runtime-process.ts
  runtime-rpc-client.ts
```

- `rpc-protocol.ts` 定义 command / response / stream event envelope。
- `jsonl-reader.ts` 和 `jsonl-writer.ts` 只负责按行读写 JSON，不包含业务逻辑。
- `runtime-rpc-server.ts` 负责从 stdin 读取 control message，调用 runtime，并把 stream event 写到 stdout。
- `runtime-process.ts` 负责启动和管理 child process。
- `runtime-rpc-client.ts` 负责发送 command、关联 command response、订阅 runtime stream event。
- runtime stdout 只输出 protocol JSONL；debug log 必须走 stderr 或日志文件，避免破坏协议。

## Stream Event Contract

第一版最小事件：

```text
run.started
message.delta
message.completed
tool.started
tool.completed
context.built
run.graph.updated
run.completed
run.failed
```

`run.graph.updated` 可以在第一版简化为 run 完成后发送一次完整 graph。后续如果要观察长时间运行的 agent，可以增量发送 graph patch。

## Run Graph View

第一版 debug 页面推荐四个 tab：

```text
Chat | Events | Run Graph | Trace
```

- `Chat`：这次 run 的聊天视图，用于对照 assistant delta；它不替代 production chat 页面。
- `Events`：按时间展示 stream events / session events，方便对照原始事实。
- `Run Graph`：用 React Flow 展示 `RunGraph`。
- `Trace`：展示 MLflow trace link 或 trace summary。

`RunGraph` 的数据来源是 Lesson 1.5 定义的 session event 派生结果：

```text
AgentEvent[]
  -> buildRunGraph(events, traceSummary?)
  -> validateRunGraph(graph)
  -> RunGraph JSON
  -> React Flow nodes / edges
```

React Flow 负责渲染，不定义 runtime contract。runtime 不应该输出 React Flow 原生 node / edge 格式，而是输出 Floris 自己的 `RunGraph` JSON。这样未来换成 macOS native graph view 时，不需要重写 agent runtime。

第一版图形表达：

- 主路径从 user message 到 stop reason。
- 每次 model request 是一个节点，显示 iteration、model、tool count、token usage。
- context build 节点显示 token estimate 和 section count。
- tool call 节点显示 tool name、status、summary。
- permission 节点显示 allow / deny / needsUserApproval。
- final synthesis 节点显示是否因为 `maxIterations` 触发。
- stop 节点显示 `assistant_done`、`provider_max_tokens`、`tool_error` 等 stop reason。

Run Graph 的重点不是“画得漂亮”，而是帮助开发者发现异常状态：

- model request 没有对应 stop / tool call。
- tool call 没有 permission event。
- permission deny 后仍然执行 tool。
- provider `max_tokens` 被误当成正常完成。
- 同一 tool call pattern 重复出现，可能进入循环。
- context token estimate 过高。
- session event 没有连到主路径。

这些 diagnostics 应该在图上标红或以侧栏列表展示。点击节点时，侧栏展示 event id、payload summary、iteration、trace span id 和相关 metrics。trace span id 可以跳到 MLflow 看 request / response preview、duration 和 token 明细。

## 设计重点

- UI 不能等整个 run 完成后一次性渲染。
- assistant message 要按 delta 追加。
- tool call 先出现 pending 状态，再更新为 success / error。
- final answer 由 message deltas 组成，不只依赖最后 JSON summary。
- control message 是私有和最小的，stream event 才是 UI 状态同步主线。
- production chat 页面只展示用户需要看到的 chat / run timeline，不展示 Run Graph、raw events 或 trace。
- debug 页面通过独立 route 访问，不从主 chat 页面提供入口。
- trace link 是深度观察入口，不替代用户可读 timeline。
- Run Graph 是控制流观察入口，不替代 session event，也不替代 MLflow trace。
- 前端 reducer 要能同时维护 chat timeline、event list 和 RunGraph view state。

## 为什么从 CLI 改为 Stream Web UI

主流 AI agent 产品的核心体验是 chat / run timeline。用户需要看到 agent 正在输出、调用 tool、拿到结果和继续生成，而不是等 terminal 打印一个完整 JSON。

Stream Web UI 可以更早暴露这些问题：

- partial message 渲染是否顺畅。
- tool pending state 是否清楚。
- stop reason 是否能被用户理解。
- state graph 是否和设计路径一致。
- permission / tool / stop transition 是否出现异常。
- trace link 是否能和一次 run 对上。

## 验收标准

- Hono server 可以从 `apps/server` 启动。
- `apps/server` 通过私有本机 RPC 连接 agent runtime child process，不直接在 Web UI 内组合 runtime。
- stream endpoint 可以输出 `run.started`、`message.delta`、`tool.started`、`tool.completed`、`run.completed`。
- 前端 reducer 可以把 stream events 合成为 assistant message 和 tool timeline。
- production chat 页面不显示 debug tabs，也不显示 debug 入口。
- debug 页面有 `Run Graph` tab。
- debug 页面可以用 React Flow 渲染 `RunGraph` nodes / edges。
- Run Graph 能展示 text-only、tool-call、max-iterations final synthesis、provider max_tokens、tool error 这几类路径。
- Run Graph diagnostics 可以展示至少 `missing_stop`、`tool_without_permission`、`provider_max_tokens_without_explicit_stop`。
- scripted provider 下能跑到 `assistant_done`。
- `bun run typecheck` 通过。
- `bun run test` 通过。
- `bun run check` 通过。

- 不做 OpenAPI endpoint。
