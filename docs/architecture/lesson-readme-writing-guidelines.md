# Lesson README 写作指南

## 目标

本文档定义 `docs/teaching/lessonN/README.md` 的写作方式。Lesson README 不是普通任务清单，也不是代码注释集合，而是一份从 0 到 1 的教学规划文档。

它要帮助用户理解：

- 为什么这一课值得做。
- 这项技术从过去到现在如何演进。
- 我们参考了哪些方案。
- 我们如何比较方案并做出选择。
- 这一课具体要实现什么。
- 哪些内容暂时不实现。
- 如何验证实现完成。

## 写作定位

Lesson README 面向共同开发和教学，不只面向执行。它必须能让用户在不看聊天记录的情况下，理解本课的技术背景、判断过程、实现边界和验收标准。

每个 Lesson README 都应该回答三个层次的问题：

1. 过去：相关技术为什么出现，经历过哪些阶段。
2. 现在：当前主流方案怎么做，各自有什么 trade-off。
3. 我们：Floris AI 这一课选择什么方案，为什么现在只做到这个程度。

## 基本结构

每个 `docs/teaching/lessonN/README.md` 默认包含：

1. 目标
2. 非目标
3. 参考资料
4. 技术文章阅读样本
5. 从参考文章抽象出的写作规则或工程判断
6. 技术演进脉络
7. 本课在整体架构中的位置
8. 参考方案对比
9. 具体小节拆分
10. 输出物
11. 小节文档要求
12. 验收标准

可以根据 lesson 内容增删小节，但不能省略“技术演进脉络”“方案对比”“本课在整体架构中的位置”“验收标准”。

## 写作规则

### 1. 从真实问题开始

不要直接列实现步骤。先解释这一课解决什么真实问题。

示例问题：

- 为什么普通 chat completion 不够？
- 为什么 agent loop 需要 stop reason？
- 为什么 context window 要可查看和可裁剪？
- 为什么 memory 不能只是一个大文本？

### 2. 写出演进路径

Lesson README 要写出相关技术从早期方案到当前方案的演进。不要只展示最终结论。

推荐格式：

```text
早期做法
  -> 暴露出的问题
  -> 中间方案
  -> 新问题
  -> 当前选择
```

### 3. 先给全局图，再拆模块

先建立整体心智模型，再进入模块细节。

推荐顺序：

1. 这一课在 Floris AI 架构中的位置。
2. 完整运行路径。
3. 模块职责拆分。
4. 每个模块的输入、输出和边界。
5. 测试和验收。

### 4. 每个模块都讲边界

每个模块至少说明：

- 负责什么。
- 不负责什么。
- 输入是什么。
- 输出是什么。
- 它和其他模块如何连接。
- 后续 lesson 会如何扩展。

### 5. 必须讲 trade-off

不能只讲“我们要做什么”。必须讲“为什么不做另一个方案”。

常见 trade-off：

- 简单 demo vs 可持续架构。
- 真实 provider vs 本地测试替身。
- 大型 class vs 函数式状态机。
- 一次性字符串 prompt vs context sections。
- 内部 typed hooks vs 用户脚本 hooks。
- in-memory store vs JSONL / SQLite persistence。

### 6. 用运行路径证明设计

每个 lesson 都应该给一个可执行或可想象的完整路径。

示例：

```text
user input
  -> context builder
  -> model provider
  -> tool call
  -> permission gate
  -> tool registry
  -> tool result
  -> final answer
  -> session event
```

### 7. 把安全和用户可控性写进主流程

如果 lesson 涉及 tool、file、shell、memory、context、agent action，就必须说明安全边界和用户可控点。即使当前 lesson 只做 stub，也要说明它为什么在主流程里。

### 8. 保留判断过程

Lesson README 要记录我们如何做判断，而不是只记录结论。

特别要写清楚：

- 放弃了哪些方案。
- 为什么现在不实现更完整能力。
- 哪些接口是为未来保留。
- 哪些设计如果改错会影响后续架构。

## 参考文章选择规则

每个 lesson 不一定都要引用 10 篇文章，但如果用户要求做深入规划，应该按以下规则选择资料：

- 优先选择和当前 lesson 技术主题直接相关的文章。
- 至少覆盖一个历史演进视角。
- 至少覆盖一个工程落地视角。
- 至少覆盖一个安全、可观测、性能或维护性视角。
- 如果来自 InfoQ 等技术媒体，要总结行文方式和工程判断，不只摘录标题。
- 外部文章只是参考，最终判断必须回到 Floris AI 的产品目标和当前阶段边界。

## 语言要求

- 保持简洁、直接、积极的创业团队口吻。
- 使用准确的软件开发术语。
- 不好翻译的术语保留 English 原语。
- 不写大厂黑话。
- 不把文档写成营销稿。
- 不堆概念，每个概念都要落到本课的实现边界。

## 和其他文档的关系

- `AGENTS.md`：定义全局协作规则和硬约束。
- `docs/architecture/*.md`：定义长期架构和实现范式。
- `docs/teaching/lessonN/README.md`：定义某一课的教学规划、技术脉络和方案选择。
- `docs/plans/lessonN-*.md`：定义某一课的具体实现步骤和状态。
- `docs/teaching/lessonN/N.x-*.md`：按小节同步写教学笔记、实现拆解、当前状态和验收标准。

## 修改规则

修改任何 `docs/teaching/lessonN/README.md` 前，必须先阅读本文档，并保证 README 的结构、语气和判断过程符合本文档要求。

如果某个 lesson README 因主题特殊需要偏离本文档，必须在 README 中说明原因。
